- 기준: HanMark 2.5.6, 원격 기본 브랜치 `2.5.6`, HEAD `11649b84ef5983f78ec3a4cc1ed69ab7bd86e651`
- Research: R-001, R-002, R-003, R-005, R-006, R-008, R-009, R-010, R-012

## 1. 권장 결정

**macOS PDF 저장 수정을 먼저 별도 릴리스하고, 2단 편집은 B 모드의 공통 흐름을 먼저 검증한 다음 A 모드까지 완성한다.**

사용자에게 제공하는 본문 옵션은 다음 세 가지다.

| 옵션 | 본문 | 이미지 |
|---|---|---|
| 1단 — 기존 | 기존 전체 폭 | 기존 동작 |
| 2단 — A 모드 | 좌→우로 이어지는 2단 | 본문 전체 폭을 차지한 뒤 2단 재개 |
| 2단 — B 모드 | 좌→우로 이어지는 2단 | 한 단의 폭에 맞춤 |

처음 업데이트한 사용자의 기본값은 1단이다. 표지·PDF 테마·머리말·꼬리말은 현재 계약을 유지하고, 본문 배치 옵션을 PDF 테마와 독립적으로 적용한다. 아래 수치와 예외 처리는 제안이며 사용자 승인이나 실제 조판 검증을 이미 받은 값이 아니다.

### 2.3 첨부 PDF 관찰

- 13페이지, 515.906 × 728.504pt, 약 182 × 257mm. HanMark의 A4와 규격이 다르다.
- SHA-256: `be2da32d67d51a9a2216a062ce1213b69092316ed20ff38b5d91f9a83ed46fcd`
- 13쪽 전체 접촉 시트를 렌더링해 본문 2단과 마지막 페이지의 채움 형태를 확인했다.
- 대표 본문 2·3·4·9쪽의 단어 좌표를 측정했다. 왼쪽 본문 시작 약 20mm, 오른쪽 본문 시작 약 92.65mm, 좌우 단어 경계 사이 공백 약 3.0~3.4mm다. 이는 글자 경계 측정이며 원본 편집기의 정확한 gutter 설정값은 아니다.

첨부 PDF는 본문 읽기 흐름의 참고 자료다. 해당 파일의 표지·판형·좁은 간격을 HanMark에 복제하지 않는다. 첨부물의 본문은 개발 지시로 취급하지 않는다.

## 3. macOS: 먼저 증상을 분리한다

사용자 후속 확인: **인쇄창은 열리지만 PDF 프린트를 선택할 수 없다는 사용자 전언이며, 요청자에게 macOS 장비가 없어 직접 확인하지 못했다.** 따라서 창 열기 자체는 현재 보고의 실패 지점이 아니다. 별도 PDF 메뉴가 없는 것인지, 프린터 목록에서 PDF 항목을 찾은 것인지는 아직 미확인이다. OS·Obsidian 버전도 미확인이다.

Apple의 표준 인쇄창에서는 프린터 목록과 PDF 저장 메뉴가 별개다. PDF 메뉴가 없다는 것, 인쇄창 자체가 안 열린다는 것, 저장한 PDF가 비어 있다는 것은 다른 문제다. [Apple 인쇄 설정](https://support.apple.com/guide/mac-help/print-settings-on-mac-prtct002/mac)

| 재현 증상 | 먼저 확인할 항목 | 수정 방향 |
|---|---|---|
| 창 정상, PDF 메뉴도 있음 | PDF 저장 위치에 대한 안내와 실제 저장 | macOS용 안내 보완, 결과 확인 |
| 창은 열리나 PDF 메뉴 없음/비활성 | OS·Electron 버전, 등록 프린터 유무 | 직접 PDF 저장 경로 검증 |
| 창이 안 열림 | 콘솔 오류, 실행 창, 포커스, 최소 Chromium | 호출 경로 또는 런타임 호환 수정 |
| 빈 PDF/일부 누락 | `.print` 클래스, print CSS, 자산 준비, DOM 정리 시점 | 렌더링/수명주기 수정 |

재현 기록은 macOS·CPU·Obsidian 앱/설치 프로그램·Electron·Chromium 버전, 등록 프린터 유무, 오류 단계, 실제 PDF 결과로 구성한다. 노트 본문·개인 경로는 진단 로그에 넣지 않는다.

Electron에는 macOS 인쇄 관련 이력들이 있지만 이번 버그와 동일하다고 단정하지 않는다. 특히 [#36897](https://github.com/electron/electron/issues/36897)은 Electron 22의 `webContents.print()`가 실패하고 `window.print()`가 작동했다는 사례다. 현재 HanMark가 이미 후자를 사용하므로 그대로 원인으로 인용할 수 없다. [#50600](https://releases.electronjs.org/pr/50600)도 옵션을 전달하는 `webContents.print()`의 수정 이력이며 현재 호출과 구분해야 한다.

### 3.1 권장 출력 구조

목표는 사용자가 PDF를 저장할 때 가상 프린터 설치나 선택에 의존하지 않는 것이다.

```text
동일한 PDF 전용 DOM·테마·자산 준비
  ├─ PDF로 저장 → PDF 바이트 생성 → FileGateway → 저장 결과
  └─ 프린터로 인쇄 → 현재 운영체제 인쇄창 → delegated
```

우선 macOS에서 직접 저장을 사용할 수 있게 검증하고, Windows/Linux의 기존 인쇄 경로도 유지한다. 다른 OS의 기본 버튼까지 바꾸는 것은 각 OS의 저장 품질 확인 후 결정한다.

Electron의 `webContents.printToPDF()`는 PDF 바이트를 반환한다. 그러나 main process API이므로 플러그인 renderer에서 바로 쓸 수 있다고 가정하면 안 된다. [Electron API](https://www.electronjs.org/docs/latest/api/web-contents#contentsprinttopdfoptions)

**첫 기술 검증에서 확정할 것:**

1. 지원 최소/현재 Obsidian에서 해당 문서 window의 PDF 생성 기능에 접근할 수 있는 경로를 확인한다. main 창과 pop-out 창을 구분한다.
2. `pdfOutputAdapter.ts` 같은 단일 경계에만 플랫폼 접근을 둔다. 공개 API와 호스트 내부 브리지를 구분해 문서화한다. 내부 브리지나 remote 기능이 필요하면 지원 버전·실패 처리·Community 검사 결과를 검증한다.
3. 기존 “Electron 우회 금지” 테스트를 단순 삭제하지 않는다. 렌더러의 금지를 유지하고, 새 어댑터에서 허용하는 기능과 금지하는 DOM 실행·파일 접근을 별도 테스트로 명시한다. R-005의 `window.print` 고정 가정은 이 검증을 통과한 새 출력 경계에 한해서 대체한다.
4. `printBackground: true`, `preferCSSPageSize: true`, A4, scale 1, 브라우저 기본 header/footer 끄기를 후보로 비교한다. 기존 named `@page`의 표지 여백 0 / 본문 여백이 그대로 나오는지 확인하고 전역 margin 옵션으로 덮어쓰지 않는다.
5. DOM·CSS·폰트·이미지를 PDF 바이트 생성 Promise가 끝날 때까지 유지한다. 그 뒤 FileGateway로 저장하고, 실패/취소/완료를 각각 반환한다. PDF 생성 중에는 중복 실행과 기존 root 삭제를 차단한다.
6. 파일 저장은 기존 FileGateway/Vault/브라우저 API를 재사용한다. Node `fs`, 별도 Python/Pandoc, 클라우드 변환을 추가하지 않는다. 비동기 PDF 생성 뒤 파일 선택기의 user activation이 유지되는지 확인하고, 필요하면 명시적 저장 버튼을 제공한다.

안정적인 호스트 접근이 없으면 직접 저장을 구현 완료로 표시하지 않는다. 가능한 대안은 같은 Editorial PDF 문서를 자체 포함 HTML로 저장해 검증된 외부 Chromium 인쇄로 연결하는 명시적 우회다. 기존 HTML exporter의 다른 디자인을 대신 내보내는 방식은 동일 결과를 보장하지 않는다. 이 우회는 임시 경로이며 macOS 앱 내부 수정 완료와 구분한다.

### 3.2 macOS 수정 완료 조건

- 프린터가 하나도 등록되지 않은 macOS에서도 실제 PDF 파일을 저장하고 다시 열 수 있다.
- 한글·표지·선택 테마·이미지·머리말·꼬리말·쪽 번호가 출력된다.
- 첫 실행, 두 번째 실행, 저장 취소, 오류 후 재시도, pop-out 창, 플러그인 unload가 검증된다.
- Windows/Linux에서 사용자가 확인한 기존 인쇄 흐름을 회귀 검사한다.
- `delegated`를 저장 성공으로 표시하지 않는다. 다운로드만 시작해 저장 확인이 불가능한 경로도 이를 구분한다.

## 4. 2단 공통 규격

### 4.1 제안 치수

| 요소 | 시작값 |
|---|---:|
| 종이 | 기존 A4 210 × 297mm |
| 본문 바깥 여백 | 좌우 20mm, 상하 22mm |
| 본문 전체 폭 | 170mm |
| 가운데 간격 | 기본 10mm, 선택 8 / 10 / 12mm |
| 단 너비 | `(170 - gap) / 2`, 기본 80mm |
| 그림과 본문 사이 | 위·아래 각각 4mm를 시작값으로 검증 |
| 가운데 구분선 | 없음 |
| 본문 글꼴/크기 | 우선 기존 9pt·1.55 유지, 실물 가독성 검사 |

10mm는 첨부 PDF에서 측정한 값이 아니라 사용자의 넉넉한 가운데 간격 요구를 위한 제안이다. 폭 170mm는 기존 본문 기준이다. A 모드의 “풀 폭”은 이 170mm를 전부 사용한다는 뜻이며, 이미지에 추가 좌우 패딩·들여쓰기·장식 테두리를 붙이지 않는다. 종이 바깥 여백까지 없애는 210mm 재단 끝 출력은 별도 요구다.

### 4.2 읽기 순서

그림이 없는 페이지 및 B 모드:

```text
현재 페이지 왼쪽 위 → 왼쪽 아래
                       ↓
현재 페이지 오른쪽 위 → 오른쪽 아래
                       ↓
다음 페이지 왼쪽 위 → …
```

문장을 단 경계에서 이어 쓰며, 블록 개수나 글자 수를 단순 반으로 나눠 배치하지 않는다. 마지막 페이지는 왼쪽부터 순서대로 채우는 것을 기본으로 하고, 억지로 마지막 양단 높이를 맞추는 옵션은 첫 버전에 추가하지 않는다.

### 4.3 설정

```ts
type EditorialPdfLayoutMode = "single" | "two-column-a" | "two-column-b";

interface EditorialPdfLayoutSettingsV1 {
  schemaVersion: 1;
  mode: EditorialPdfLayoutMode;
  columnGapMm: 8 | 10 | 12;
}
```

- PDF 설정 탭: 기본 본문 배치와 가운데 간격.
- PDF 내보내기 창: 현재 배치 선택, A/B 작은 도식, 이번 내보내기용 변경.
- 내보내기 창 변경은 이번 작업에 적용하고, 기본값 저장은 명시적 동작으로 분리한다.
- PDF 테마 라이브러리/JSON에는 당장 레이아웃을 넣지 않는다. 기존 테마를 세 배치에 모두 사용할 수 있다.
- 설정 버전 9→10을 제안한다. 미설정/손상된 값은 `single`, 간격 10mm로 정규화한다. 기존 테마와 알 수 없는 상위 필드 보존, 저장 실패 rollback, 재정규화 동일성을 검사한다.
- 내보내기 클릭 시 theme와 layout을 함께 복사해 자산 준비 전에 snapshot을 고정한다.

## 5. B 모드: 한 단 안에서 이미지 배치

1. 텍스트와 그림이 같은 단 흐름을 따른다.
2. 일반 그림은 해당 단 너비 100%에 맞추며 종횡비를 유지한다. 기본 80mm다.
3. 현재 단에 그림 전체가 들어가지 않으면 다음 단, 오른쪽 단도 끝났으면 다음 페이지 왼쪽 단으로 이동한다.
4. 이미지 전후 여백을 포함해 맞는지 판단한다. 단 사이에 걸치거나 다른 단을 침범하면 실패다.
5. 아주 긴 그림은 7절의 예외 계약을 적용한다.

현재 `max-width:100%`만으로는 작은 원본을 항상 단 폭까지 확대하지 않는다. 새로운 모드에 명시적 폭과 비율 규칙이 필요하다. 저해상도 이미지의 확대가 화질을 개선하지는 않지만, 사용자가 요청한 폭 맞춤을 조용히 다른 규칙으로 바꾸지 않는다.

## 6. A 모드: 전체 폭 그림과 2단 재개

한 페이지는 필요에 따라 여러 가로 구역으로 나뉜다.

```text
┌──────────────────────────────────┐
│          기존 머리말             │
├──────────────┬────┬──────────────┤
│ ① 앞 본문    │간격│ ② 앞 본문    │
│ 왼쪽 ↓       │10mm│ 오른쪽 ↓     │
├──────────────┴────┴──────────────┤
│           위 여백 4mm            │
│ ③ 그림 — 기존 본문 전체 폭 170mm │
│           아래 여백 4mm          │
├──────────────┬────┬──────────────┤
│ ④ 뒤 본문    │간격│ ⑤ 뒤 본문    │
│ 왼쪽 ↓       │10mm│ 오른쪽 ↓     │
├──────────────┴────┴──────────────┤
│          기존 꼬리말             │
└──────────────────────────────────┘
```

규칙:

- 그림 앞 텍스트는 그림 위, 뒤 텍스트는 그림 아래에서 계속 읽는다. 후속 문장을 빈 곳에 먼저 넣거나 그림을 임의의 먼 페이지로 띄우지 않는다.
- 그림 앞 두 단은 해당 구역의 높이를 맞출 수 있다. 순서는 항상 왼쪽→오른쪽이다.
- 페이지 첫 내용이 그림이면 상단 본문 구역은 비어 있을 수 있다. 마지막 내용이 그림이면 하단 구역은 없을 수 있다.
- 남은 공간에 그림과 여백이 들어가지 않으면 그림을 다음 페이지 전체 폭 위치로 옮긴다. 뒤 본문은 그 뒤에 이어진다.
- 그림 아래에 유효한 본문 줄을 넣을 공간이 없으면 다음 페이지 왼쪽 단에서 재개한다.
- 연속 그림은 원문 순서대로 배치하고, 인접 여백이 불필요하게 두 배가 되지 않도록 간격을 정규화한다.
- 이미지 없는 문서에서는 A와 B의 본문 흐름이 같아야 한다.

## 7. 먼저 명확히 할 예외

### 7.1 스크린샷 인식과 중첩 이미지

현재 모델에는 “스크린샷”이라는 별도 타입이 없다. 파일명이나 그림 내용으로 추측하지 않고, 우선 Markdown의 일반 본문 이미지를 A/B 배치 대상으로 삼는 것을 제안한다. 단독 이미지, 링크로 감싼 이미지, 한 문단의 여러 이미지, 텍스트 사이 이미지가 대상이다. `alt`는 대체 텍스트로 유지하고 자동으로 캡션으로 바꾸지 않는다.

PDF 전용 중간 모델에서 `text → figure → text`로 분해한다. 공유 `editorialDocument.ts`를 조판 때문에 바꾸지 않고 HTML/DOCX/HWPX에 영향이 없게 한다.

목록·인용·callout 안 이미지를 A 모드에서 전체 폭으로 만들 때는 앞뒤 컨테이너를 분리하고 목록 번호·인용 관계를 이어야 한다. 표 셀 안 이미지나 작은 인라인 아이콘은 문맥 관계가 달라 별도 fixture와 정책 결정이 필요하다. 특히 표 전체를 넓히는 것만으로 셀 이미지가 170mm가 되지는 않는다.

표 셀의 스크린샷도 무조건 전체 폭이어야 한다면, 그림을 표 밖 전체 폭 figure로 옮기고 원래 셀에 해당 그림 참조를 유지하는 방안을 검토한다. 이 변환은 읽기 구조에 영향을 주므로 일반 단독 그림과 같은 완료 판정에 묻어 넣지 않는다. A 모드의 “모든 스크린샷” 지원을 주장하기 전에 이 정책과 회귀 검증을 확정해야 한다.

### 7.2 세로로 아주 긴 스크린샷

폭 170mm와 종횡비를 유지했을 때 높이가 본문 253mm보다 큰 그림은 한 페이지에 모두 들어갈 수 없다. B의 80mm 폭에서도 매우 긴 그림은 같은 문제가 생긴다.

**권장안:** 목표 폭을 유지한 채 그림을 연속 세로 구간으로 나눠 여러 페이지/단에 이어 출력한다. 각 구간의 원본 픽셀 범위는 겹치거나 빠지지 않아야 하고, 일반 그림은 쪼개지 않는다. PNG/JPEG 등 실제 지원 형식의 디코딩 후 비율과 구간 높이를 계산한다. 구현 방식은 동일 이미지의 표시 구간 분할을 우선 검증하고 불필요한 재압축을 피한다.

이 처리는 아직 확정 구현이 아니다. 한 페이지 맞춤 축소를 선택하면 A의 전체 폭 약속을 깨뜨릴 수 있다. `max-height:225mm`나 `object-fit:contain`만 남겨 놓고 “전체 폭 보장”으로 설명해서는 안 된다. 이 예외에 대한 시제품을 보고 최종 정책을 확정한다.

### 7.3 제목·표·코드

- 제목이 단 끝에 혼자 남지 않게 다음 본문과 함께 이동한다. 기존 `avoid-page`만으로 단 나눔까지 막는다고 가정하지 않는다.
- 문단은 기존 widow/orphan 3줄을 출발점으로 삼고, 충돌 시 누락 없이 진행되게 한다.
- 코드·표·callout의 분할 임계값은 실제 단 너비와 패딩에 맞춘다. 기존 88/72 문자 추정값을 그대로 재사용하지 않는다.
- 큰 표를 무조건 축소해 글자가 읽히지 않게 만들지 않는다. 현재 행/셀 분해 대체 출력에 단 너비를 반영하고, 표 머리말 반복과 의미 순서를 검사한다.
- 일반 제목·표·코드를 모두 전체 폭으로 만드는 것은 이번 A 모드의 기본 규칙이 아니다. 전체 폭 예외는 우선 그림에 적용한다.

## 8. 조판 엔진 선택

### 8.1 우선 검증: Chromium의 다단 인쇄

본문에 `column-count:2`, 명시적 `column-gap`, 순차 채움을 적용하고 A의 figure에 `column-span:all`을 사용하는 시제품을 먼저 만든다. 표지는 다단 컨테이너 밖에 둔다. W3C의 다단 모델은 페이지 간 흐름과 전체 단을 가로지르는 요소를 정의한다. span 앞 구역은 높이를 맞추는 동작이 있으므로 A의 구역 흐름과 함께 검증한다. [CSS Multi-column](https://www.w3.org/TR/css-multicol-1/)

중요한 구현 제약:

- 본문 전체를 고정 높이 다단 박스로 만들지 않는다. 가로로 제3·제4의 넘침 단이 생기는 방식과 페이지 인쇄를 구분한다.
- 화면에 보이는 두 박스만으로 페이지 흐름을 판정하지 않는다. 실제 생성 PDF에서 검증한다.
- figure는 PDF 전용 구조에서 명확한 블록으로 만든다. 중첩 컨테이너가 span 동작을 막는 사례를 검사한다.
- 원문 순서, 단·페이지 경계, overflow, long-block 분할, print CSS 격리를 함께 바꾼다. CSS 몇 줄 추가만으로 완료하지 않는다.

### 8.2 실제 출력 시제품의 판정

최소 지원 Chromium 131과 실제 Obsidian 런타임에서 다음 대표 문서를 출력한다.

1. 이미지 없는 긴 문서와 중간에서 끝나는 마지막 페이지.
2. 단 경계의 짧은/긴 이미지, 본문 시작/중간/끝 그림.
3. A 모드에서 페이지 경계 직전의 전체 폭 그림과 바로 뒤의 제목.
4. 연속 그림과 아주 긴 세로 그림.
5. 긴 한글·영문 URL·코드·표·목록·callout 및 중첩 이미지.

CSS 기반 경로가 기준을 충족하면 유지한다. 실패 사례가 지속되면 두 모드가 공유하는 명시적 페이지/구역 조판기로 전환한다. 내용 누락·잘림을 임의 축소로 숨기는 fallback은 사용하지 않는다.

### 8.3 필요할 때의 명시적 조판기

- 페이지별 본문 170 × 253mm를 기준으로 가용 영역을 만든다.
- 텍스트 구역은 두 단, figure 구역은 전체 폭으로 구성한다.
- 로드 완료된 실제 폰트와 최종 출력과 같은 CSS에서 DOM 높이·줄 범위를 측정한다. 현재 화면용 숨김 root의 치수를 print CSS 치수로 오인하지 않는다.
- 글꼴 기준 줄 단위로 문단을 나누고 inline 서식·링크·한글 grapheme를 유지한다.
- 매 반복에서 텍스트/이미지 구간이 진행되거나 실패를 반환하도록 해 무한 페이지 생성과 무한 루프를 막는다.
- 페이지·figure별 stable ID와 원문 범위를 기록해 내용 보존을 검사한다.
- 머리말·꼬리말의 기존 `@page`와 명시적 페이지 wrapper가 이중 페이지·빈 쪽을 만들지 않는지 확인한다.

이 조판기는 구현 범위가 크다. 첫 단계부터 무조건 만들지 않고 실제 CSS 인쇄 결과를 근거로 선택한다.

## 11. 검증 계획

### 자동 검증

- 기본값/누락 필드에서는 기존 1단 DOM·CSS·표지·테마 계약 유지.
- 설정 normalization의 반복 동일성, invalid enum/NaN, 저장 실패 rollback, 테마 JSON 보존.
- 내용 sentinel이 원문 순서대로 정확히 한 번 출력되는지 검사. 별도로 의도한 표 머리말 반복은 구분.
- 이미지 URL·alt·링크·inline 서식 보존, 혼합 문단과 중첩 컨테이너 분해.
- 모드별 이미지 목표 폭, 여백, 원본 종횡비, 긴 이미지 구간 합계·누락/중복 검사.
- PDF 생성 Promise 지연·reject·취소·중복 클릭 중 DOM과 자산 수명주기.
- 실제 Chromium 출력 fixture를 만들어 텍스트 좌표와 이미지 경계, 페이지 순서를 검사. 기존 모의 DOM 테스트만으로 조판 정확성을 주장하지 않음.
- `npm run check`, 배포 의존성 audit, diff 검사. 런타임 API 변경은 Community 검사 기준을 새 SHA로 재검증.

### 실제 출력 검사

Windows·macOS·Linux에서 프린터 없음/있음, 첫/반복 실행, 취소/재시도를 확인한다. macOS는 최소 지원 환경과 현재 환경을 구분한다. 지원할 CPU 조합도 기록한다.

공통 출력 기준:

- 표지 한 쪽과 기존 52/48·문구·색 보존, 불필요한 빈 쪽 없음.
- 본문 폭 170mm, 기본 간격 10mm, 단 폭 80mm. 직접 PDF에서 목표 오차는 0.5mm 이내로 제안.
- A 일반 그림은 170mm, B 일반 그림은 단 폭에 맞고 왜곡·잘림 없음.
- 텍스트의 좌→우→다음 페이지 순서, A에서 그림 전후 구역 순서 유지.
- 헤더·푸터·쪽 번호와 본문 충돌 없음.
- 제목만 단 끝에 남음, 읽기 어려운 표 축소, URL/코드의 가운데 침범 없음.
- 긴 그림의 세로 구간 누락·중복 없음.
- 실제 PDF 텍스트 추출·한글 선택·링크 상태도 기록. 직접 저장 결과와 OS 프린터 결과가 같은 텍스트 특성을 갖는다고 가정하지 않음.

현재는 macOS 장비에서 재현하지 않았고, 새 2단 코드를 작성하거나 plugin 출력 시험을 실행하지 않았다. 위 검증은 구현 단계의 완료 조건이다.

## 12. 남은 결정

1. 인쇄창이 열리는 것은 사용자 전언으로 확인했다. 별도 PDF 메뉴의 존재/활성 상태와 해당 런타임 버전은 미확인이다. macOS 장비를 가진 검증자 또는 실제 앱을 실행할 수 있는 시험 환경이 필요하다.
2. Obsidian에서 안정적으로 쓸 직접 PDF 저장 호출 경로와 Community 검사 결과.
3. 스크린샷과 인라인 아이콘의 구분 정책, 표 셀 이미지의 A 모드 변환.
4. 아주 긴 그림의 연속 분할 출력 시제품과 최종 동작.
5. 10mm 기본 간격과 4mm 그림 여백의 실제 출력 평가.

이 항목들은 조사 사실과 분리한 구현 전 결정 사항이다. macOS 수정과 일반 2단 시제품은 필요한 항목부터 순서대로 해결한다.
