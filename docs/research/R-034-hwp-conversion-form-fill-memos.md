# R-034 — HWP를 HWPX로 변환, HWP 5.x 양식 채우기, 주석을 한글 메모로

- 상태: REQUIRED (3~6절 사실은 CONFIRMED, 8절 미해결 항목은 PROPOSED)
- 작성일: 2026-11-18
- 기준 버전/커밋: 3.0.0 준비 브랜치 `3.0.0-dev` 1c79c04 → 작업 브랜치 `m4-convert`, Kordoc 4.25.0
- 관련 문서: R-023(비교·양식 채우기), R-029(엔진 이식), R-032(가져오기 표기)
- 담당 범위: `src/io/hwpConvert.ts`, `src/ui/hwpConvertFlow.ts`, `src/io/hwpxMemos.ts`, 양식 채우기의 HWP 입력, 보기 화면·파일 메뉴·명령 연결

## 1. 조사 질문

Kordoc 4.25.0이 새로 낸 세 기능(HWP → HWPX 서식 보존 변환, HWP 5.x 양식 채우기, 메모 달기)을 HanMark의 오프라인·결정적 변환 계약과 번들 하드닝을 지키면서 어떻게 들이는가? 노트 쪽 메모 표기는 무엇으로 정하는가?

## 2. 범위

### 포함

- HWP 5.x·3.x를 HWPX로 바꿔 볼트에 쓰는 흐름(보기 화면 단추, 파일 메뉴 한 개·여러 개, 명령)
- 양식 채우기가 HWP 5.x 양식을 받는 것
- HWPX 내보내기에서 노트의 주석을 한글 메모로 다는 것, 가져온 메모와의 왕복
- 번들 안에서 한/글 자동화 엔진에 닿지 않는다는 검증

### 제외

- 원본 한글 파일에 되쓰기(저장). 지금 HanMark에는 이 기능이 없고(R-032 12절) 이번에도 만들지 않는다.
- HWPX → HWP 저장(`hwpxToHwp`). 32MB 선택 의존성(`@rhwp/core`)이 필요하다.
- 내보내기 창 안의 스위치(8절).

## 3. 조사 방법과 증거

## 4. 확인된 사실

### 4-1. 변환

1. Kordoc의 변환 진입점은 둘이다. `hwpToHwpx`는 HWP 5.x만 서식 그대로 바꾼다. `convertToHwpx`는 그것을 감싸 HWP 3.x·HWPML(글·표만, 기본 서식)과 한/글 저장 엔진 선택(`engine`)을 더한다.
2. `convertToHwpx`는 HWP 3.x 경로에서 Kordoc의 진입 모듈 전체(`index.js`)를 동적으로 불러온다. 이것을 쓰면 HanMark 번들에 OCR 안내문·인쇄·HWP 저장 코드가 딸려 와 `main.js`가 6,253,129바이트가 되고, 번들 검사가 `onnxruntime-node`·`@rhwp/core`·`puppeteer-core` 흔적으로 실패했다(직접 확인). `hwpToHwpx`만 쓰면 6,139,897바이트이고 검사를 통과한다.
3. `engine`을 `"hancom"`이나 `"auto"`로 주면 순정 Kordoc은 Windows에서 PowerShell로 한/글을 띄우려 한다(Node에서 직접 확인: `REGDB_E_CLASSNOTREG`). HanMark 번들에서는 R-029 하드닝이 이 분기를 거부 문장으로 바꿔 두어 두 값 모두 "HanMark does not bundle Hancom Office automation."으로 끝난다(테스트). HanMark 코드는 `convertToHwpx`를 부르지 않는다(테스트).
4. Kordoc의 변환 결과는 실행마다 바이트가 달라질 수 있다(ZIP 날짜. 합성 HWP 5.x에서 2초 간격 두 번이 달랐다). HanMark의 `finalizeHwpxPackage`를 거치면 같은 문서가 같은 바이트가 된다.
5. 실제 문서(연구계획서 HWP 5.x, 2,969,088바이트): 변환 약 130ms, HWPX 3,543,468바이트, `validateHwpx` 통과, 두 번 변환 바이트 동일. 원본과 변환본을 같은 옵션으로 다시 읽은 결과: 글자(문자·숫자) 13,076자 = 13,076자로 순서까지 동일, 표 10개 = 10개로 칸 격자 동일, 그림 3장 = 3장, 변환본 렌더 23쪽. 양식 필드는 38개가 읽혔다.
6. 같은 문서를 HWP로 읽을 때와 HWPX로 읽을 때 Markdown 표지가 다르다(HWP는 스타일로 `#` 제목, HWPX는 굵은 글씨·밑줄). 글자는 같다. 비교는 표지를 빼고 했다.
7. 암호 걸린 HWP 3.x(DES-ECB, 공개 시험 자료, 101,244바이트): 암호 없이 읽으면 `ENCRYPTED`가 나와 암호 입력으로 이어진다. 맞는 암호로 변환하면 글자 18,695자 = 18,695자, 표 2개 = 2개(격자 동일), 그림 2장 = 2장, 렌더 16쪽, 검증 통과, 두 번 변환 바이트 동일. BMP 그림은 PNG로 바뀌어 들어간다.
8. 배포용(열람 제한) HWP와 암호 걸린 HWP 5.x는 시험할 문서가 없어 확인하지 못했다. Kordoc 변경 기록(4.24.41)은 배포용 문서 변환을 허용한다고 적는다.

### 4-2. 양식 채우기

1. `fillHwpx`와 `extractClickHereFields`는 HWPX만 받는다. HWP 5.x 양식은 위 변환(`preserve`)을 거친 HWPX로 읽고 채운다. 결과는 항상 HWPX다. Kordoc의 `fillForm(…, "hwpx-preserve")`가 HWP에 대해 하는 일과 같다.
2. 합성 HWP 5.x 문서(글상자 안 4×6 결재표)에서 필드 10개가 읽혔고, 한 칸을 채운 결과는 검증을 통과하며 이웃 이름표 7개가 그대로 남았다. 두 번 채운 결과는 바이트가 같다.
3. HWP 3.x 양식은 변환이 서식을 새로 만들기 때문에 양식으로 받지 않고 이유를 알린다.
4. 이름표 옆 칸 채우기(이름표 4개 보존)와 날인 표시 `(인)` 보존을 생성한 HWPX 양식으로 확인했다(4.21~4.24 수정 사항).

### 4-3. 메모

1. `addMemoHwpx(hwpx, [{ anchor, text, author, occurrence }], now)`는 앵커 글을 문서 순서로, **한 문단 안에서** 찾는다. 못 찾으면 예외를 던진다(호출 전체가 실패한다). 그래서 HanMark는 메모를 하나씩 단다.
2. `parse(…, { memos: true })`는 `memos`(앵커, 문단, 문단 안 위치, 작성자, 시각, 번호)를 돌려주고, 노트 끝에 `---` 뒤 굵은 "메모" 제목과 번호 목록(`N. (작성자, 시각) 「앵커」 — 글`)을 붙인다. 메모 안 줄바꿈은 목록에서 ` / `로 이어진다.
3. `now`를 고정하면 같은 입력의 메모 달기 결과는 (HanMark 마감을 거친 뒤) 바이트가 같다.

## 5. 해석과 제안 (구현한 것)

### 5-1. 변환 흐름

- `convertHwpToHwpx`: OLE2 파일(HWP 5.x)은 `hwpToHwpx`로 바꾼다. 그 밖의 한글 문서(HWP 3.x, HWPML)는 HanMark가 이미 가진 조각으로 다시 만든다: 가져오기와 같은 `parse`(틀 표 유지, 첨자 켬)로 읽고, 빠른 HWPX 생성기로 쓰고, 읽어 낸 그림을 그대로 넣는다. 한글 문서가 아니면 거절한다.
- 어느 경로든 결정적 포장 → `validateHwpx` 통과 뒤에만 결과를 돌려준다. 실패하면 같은 바이트를 `parse`로 읽어 가져오기와 같은 문장(암호 필요 등)으로 설명한다.
- `convertHwpFiles`: 원본 옆에 `이름.hwpx`, 있으면 `이름 (1).hwpx`…로 쓴다. 덮어쓰지 않는다. 암호는 가져오기와 같은 창으로 세 번까지 묻고 메모리에만 둔다. 여러 파일은 진행 알림의 "남은 파일 멈추기"로 파일 사이에서 멈춘다. 한 파일이 깨끗하게 끝나면 변환본을 보기 화면으로 열고, 그 밖에는 보고 창(저장 경로, 서식 보존 여부, 엔진 알림, 실패 이유와 원문)을 띄운다.
- 진입점: 한글 문서 보기 화면의 "HWPX로 변환"(HWP에서만), 파일 메뉴(한 개·여러 개), 명령 "지금 열린 HWP 문서를 HWPX로 변환".

### 5-2. 양식

- `formTemplateHwpx`가 양식 바이트를 HWPX로 맞춘다. `readFormFields`와 `fillFormHwpx`가 이 한 곳을 지난다.
- HWP 양식으로 만든 노트에만 `hanmark-form-format: hwp` 속성을 쓴다. HWPX 양식 노트는 예전과 같은 속성만 가진다. 양식 해시는 원본(HWP) 바이트로 계산해, 원본이 바뀌면 새 필드를 더하는 기존 동작이 그대로다.

### 5-3. 메모 표기: 형광펜 바로 뒤의 주석

```
==추진 일정==%%1월 워크숍 날짜 확인 필요%%
==가평==%%@안창현: 대관료 문의%%
```

- 형광펜이 메모가 붙는 글(한/글이 칠하는 범위), 바로 뒤 주석이 메모 글이다. `@이름:`으로 시작하면 작성자, 주석 안 줄바꿈은 메모 문단이다.
- 고른 이유
  - 둘 다 Obsidian 사용자가 이미 쓰는 표기다. 읽기 화면에서 형광펜은 보이고 주석은 숨는다. 한/글의 메모가 보이는 모양(칠한 범위 + 따로 뜨는 글)과 같다.
  - 메모는 "어느 글에 붙는가"가 있어야 한다. 주석만으로는 범위를 알 수 없고(앞 낱말? 문장? 문단?), 추측하면 틀린 자리에 붙는다. 형광펜이 범위를 정확히 준다.
  - 각주식 표기는 각주(실제 각주로 내보냄)와 뜻이 겹치고, 전용 콜아웃은 본문 흐름에서 떨어져 범위를 다시 적어야 한다.
- 형광펜 없는 주석은 지금처럼 어떤 내보내기에도 나가지 않는다. 코드 블록과 인라인 코드 안은 읽지 않는다.
- 설정 "주석을 한글 메모로"(기본 꺼짐)가 켜졌을 때만 동작한다. 꺼져 있으면 내보내기 경로가 메모 코드를 지나지 않고, 켜져 있어도 짝이 없으면 생성 결과 객체를 그대로 돌려준다(같은 바이트).
- 켜면 형광펜 표지는 본문에서 빠진다(메모가 범위를 칠한다). 그래서 왕복해도 형광펜이 겹쳐 쌓이지 않는다.

### 5-4. 메모를 제자리에 다는 방법

- 같은 글이 문서에 여러 번 나올 수 있고, 생성한 문서에는 노트에 없던 반복이 생긴다(목차가 제목을 되풀이한다). 그래서 노트에서 센 순번으로 먼저 달고, 단 메모를 다시 읽어 그 문단이 노트의 문단(앵커 앞뒤 12자)과 맞는지 본다. 다르면 다음 순번을 시도한다(12번까지).
- 글은 있는데 문단이 다르게 읽히면(틀 안 제목 등) 첫 등장에 단다. 글을 한 문단 안에서 찾지 못하면 달지 않고 보고서에 앵커를 적는다.
- 시각은 내보낸 날 0시로 넣는다. 같은 날 같은 노트는 같은 바이트다.

### 5-5. 가져온 메모와의 왕복

- 가져오기에서 "한글 메모 가져오기"를 켜면, 엔진이 노트 끝에 적은 목록의 메모를 본문의 앵커 자리로 옮겨 위 표기로 쓴다. 옮기지 못한 메모는 목록에 남는다.
- 확인한 왕복: 메모 3개(본문 2, 표 칸 1)를 단 HWPX → 가져오기 → 본문 2개가 표기로 들어가고 표 칸 1개는 목록에 남음 → 다시 내보내기 → 본문 2개가 같은 앵커·같은 글·같은 작성자로 돌아옴.

## 6. 대안과 기각 사유

| 대안 | 장점 | 위험/기각 사유 | 재검토 조건 |
|---|---|---|---|
| Kordoc `convertToHwpx`를 그대로 부름 | 코드 한 줄, HWP 3.x도 한 번에 | 진입 모듈 전체가 번들에 들어와 +192KB, 번들 검사 실패(OCR·인쇄·HWP 저장 흔적). 한/글 엔진 선택지가 호출 지점에 생긴다 | 상위가 진입 모듈을 불러오지 않게 바꿀 때 |
| 변환 결과를 원본 자리에 덮어쓰기 | 파일 하나 | 원본을 잃는다 | 없음 |
| 주석 전부를 앞 낱말의 메모로 | 형광펜 불필요 | 범위 추측. 숨기려고 쓴 주석이 문서에 실린다 | 없음 |
| 메모 앵커에 표시 문자를 심어 위치 고정 | 순번 탐색 불필요 | 보이지 않는 문자는 엔진의 정리 단계가 지울 수 있고, 폭 계산(틀 맞춤)에 영향을 준다 | 엔진이 위치 지정 API를 낼 때 |
| 가져온 메모를 목록 그대로 두고 내보내기가 목록을 읽음 | 가져오기 무수정 | 사람이 쓰기 어려운 표기가 둘째 문법이 된다 | 없음 |

## 7. 한계와 미해결 질문

- 메모 앵커는 한 문단 안에 있어야 한다(엔진 제약). 문단을 넘는 형광펜은 달리지 않고 보고된다.
- 표 칸 안 메모는 내보낼 때는 달리지만, 가져올 때는 본문으로 옮기지 않고 목록에 남긴다(표 줄의 표기를 건드리지 않기 위해). 그래서 표 칸 메모는 왕복되지 않는다.
- 가져온 메모의 시각은 왕복에서 보존되지 않는다(내보낸 날로 바뀐다). 작성자는 `@이름:`으로 보존된다. 작성자가 없으면 "HanMark"로 적힌다.
- 메모가 많은 큰 문서는 메모마다 문서를 한 번 다시 읽어 느려진다.
- HWPX 미리보기는 메모를 그리지 않는다. 메모는 내보낸 파일에만 있다.
- 배포용 HWP, 암호 걸린 HWP 5.x 변환은 문서가 없어 확인하지 못했다.
- 한컴오피스에서 변환본과 메모가 어떻게 보이는지는 확인하지 못했다.
